# RachBase Go-Live Audit

**Date:** 3 Sep 2026 · **Target launch:** ~13 Sep 2026 (10 days)
**Scope:** rachbase-backend, rachbase-web, baas-* (auth/gateway/services/storage/functions), runtime-agent, site-controller, packages/* (billing, core, identity, ui…), ops docs, repo hygiene. rachdev-* apps excluded per your instruction.
**Method:** four parallel deep audits (security · billing correctness · reliability/ops · code quality & frontend) over a snapshot of your working tree (including uncommitted changes), followed by direct verification of every launch-blocking claim against source. Findings below carry file:line evidence; anything not confirmed in code is marked "verify".

---

## Verdict

**RachBase is not launchable in its current state, but a focused 10 days gets you to a credible launch — if you cut scope on the SLA and block one product path.** The architecture underneath is better than typical for this stage (the outbox/reconciler machinery, payment-security core, region-native pricing catalog, and migration tooling are all genuinely solid, and all 25 existing billing tests pass). The problems cluster in four places: **zero backups** on a product whose job is holding customer data, **money bugs** (GST never charged, two revenue leaks, a payment-amount bypass), **tenant isolation seams** (shared object storage, subdomain takeover, token-leaking redirect), and **the app doesn't currently build/deploy** (two hard build blockers plus a deploy-config contradiction).

The 99.95% SLA you've published cannot be honestly measured or met on a single Railway instance with an in-process prober — launch at **99.9% without credits** (you also currently publish two contradictory SLA pages) and raise it later with data.

## P0 — Launch blockers (fix before go-live)

### 1. No backups of anything — and customer DB containers lose all data on restart
The single worst finding, and it confirms your own instinct. There is **no backup automation anywhere in the codebase**: not for the control-plane Postgres (users, tenants, billing, invoices, outbox), not for BaaS project databases (`baasDb.js:87-131` provisions `baas_<ref>` DBs with no dump/WAL archiving), not for tenant-VM Postgres (`postgresProvision.js`), not for SeaweedFS object bytes. The only `pg_dump` in the repo is in a manual migration doc.

Worse: **container-path databases have no persistent volume at all.** The only workload renderer (`site-controller/src/renderers/manifests.js:328-381`) mounts only `emptyDir` scratch — no PVC/StatefulSet support exists (zero grep hits). A customer who deploys a Postgres image gets a database that is **wiped on every pod reschedule, node reboot, or redeploy**, while your integration doc promises "Postgres image + volume."

**Fix (3–4 days total):** enable Railway PG backups + verify a restore today (~1h); wal-g or pgBackRest with WAL archiving to R2/Wasabi for the BaaS cluster + nightly per-project `pg_dump` (~2 days incl. one rehearsed restore); nightly dump timer added to `postgresProvision.js` (~0.5d); write RUNBOOK-restore.md. **For launch, block database-type images on the container path** (1–2h guardrail) and route DB needs to the VM path until PVCs land.

### 2. Cross-tenant data breach: object storage is shared across all projects, keyed only by bucket name
`baas-storage/index.js:65` addresses objects as `/buckets/${bucket}/${key}` on **one shared SeaweedFS filer** — every project's storage container gets the same `SEAWEEDFS_FILER_URL` (`baasBundle.js:55`). Bucket *metadata* is per-project but the *bytes* are global: tenant B creates a bucket named `avatars` in their own project and can read/write/delete tenant A's `avatars` objects. Bucket names are guessable (`uploads`, `public`, `avatars`).
**Fix:** namespace the filer path by project ref (`/buckets/${ref}--${bucket}/…`) and migrate existing objects. Needs a data migration — start early.

### 3. GST is never charged — and checkout shows the GST-inclusive price while charging ex-GST
`proSubscription.js:177` (base), `:240` (containers), resize orders, and `baasBilling.js:30-37` all create Razorpay subscriptions/orders at the **ex-GST catalog amount**. There is not a single tax call in the entire Pro path (verified: zero gst/tax references in proSubscription.js), despite catalog.json's own comment ("India amounts are ex-GST, 18% added at checkout") and the marketing page promising "+ GST". Meanwhile `checkout/page.tsx:557,789,1113` **displays** the tax-inclusive total from the tax quote — customer sees ₹590/mo, gets charged ₹500/mo.
**Impact:** a 15.25% haircut on all India recurring revenue (you must remit GST out of the ₹500), displayed-vs-charged mismatch, and — compounding — **Pro charges generate no invoices at all** (`paymentController.js:162` only issues invoices for the legacy `subscriptions` table; `pro_subscriptions` rows are invisible to it). India law requires a GST tax invoice per charge. The legacy VM path (`purchase.js`) does this correctly — copy its pattern.

### 4. Payment-amount bypass: pay for the cheapest thing, get the most expensive fulfilled
`expansionController.js:326-371` and `:587-642` verify only the Razorpay *signature*, never the *amount* — the codebase's own `paymentSecurity` docstring warns the signature "says nothing about whether the money actually moved," and `purchase.js` correctly follows up with a captured-amount check; the expansion flows don't. Attack: create+pay the cheapest order, then call verify with an expensive `package_id` — the row records **full package price as amount_paid** and fulfilment provisions it. No uniqueness on `razorpay_order_id` either, so one paid order replays into multiple fulfilments. Related: `containerBilling.js:55` re-implements HMAC verification with `RAZORPAY_KEY_SECRET || ''` — with the env var missing, **signatures verify against an empty key** (used by both resize-verify paths at `projectController.js:481,750`). Same empty-fallback bug on the GitHub webhook secret (`deploymentController.js:28-31,1128`).
**Fix:** use `paymentSecurity.verifyPaymentCaptured`/`assertPaymentMatches` in all four places; unique index on order id; make missing secrets throw (mirror `paymentSecurity.secret()`).

### 5. Two subscription revenue leaks
**(a) Draft-delete promotion leak** (`proSubscription.js:273-283`, verified): deleting ANY service without a live subscription — including a draft or pending-checkout service that never occupied an allowance slot — triggers the "a free slot opened" promotion, which **cancels the oldest paying container's Razorpay subscription while the container keeps running**. One click, repeatable, ₹500/mo per paying container. Fix: only promote when the deleted service actually held a free slot (was `online`, shared, past draft/pending).
**(b) Nothing stops workloads when money stops.** Terminal webhook events and `/api/site/unsubscribe` only UPDATE `services.status` in the DB (`proSubscription.js:341,358`; `siteController.js:231`) — no `app.delete`/`tenant.suspend` outbox op is ever enqueued, and the reconciler re-asserts desired state, not stop-changes. A customer who cancels keeps containers running free, indefinitely. Also `tenantController.deleteTenant` (`:149-199`) never cancels Razorpay subs — a deleted tenant keeps **being charged for up to 10 years** (`total_count: 120`) with no user left who can unsubscribe.

### 6. The app doesn't build or deploy right now
Three independent blockers, each verified: (a) `dashboard/billing/page.tsx:394` and `dashboard/deployment/page.tsx` call `useSearchParams()` with **zero Suspense boundary** — `next build` fails on Next 14.2 (every other page is correctly wrapped; these two were missed); (b) `next.config.mjs` removed `output: "standalone"` but `railway.json` says `builder: DOCKERFILE` and the Dockerfile copies `.next/standalone` — **the image build fails**; pick one path; (c) `RELEASE_CHECKLIST.md:32` says to wire `DATABASE_URL`, and `validateEnv` accepts it — but the shared pool (`packages/core/src/config/db.js:10-15`) reads **only `DB_*` vars**, so a Railway-style deploy boots green (`/health` doesn't touch the DB) and 500s on every real request against localhost:5432.

### 7. Subdomain/DNS takeover across tenants
Three disjoint hostname namespaces live under `*.rachbase.app` (VM auto-domains in `deployment_domains`, shared-container `services.public_host`, BaaS `<ref>.rachbase.app`), but `addAutoDomain` (`deploymentController.js:966-1005`) checks only the first — and `godaddy.upsertARecord` **deletes any existing A record for the name**. A tenant can claim another tenant's app slug or project ref as their VM subdomain, hijack the DNS (incl. a BaaS project's auth endpoint where user JWTs flow), and get a Let's Encrypt cert. Fix: one global claimed-hosts registry with a unique index; never upsert DNS over a record you didn't create.

### 8. BaaS auth leaks session tokens via unvalidated `redirect_to`
`baas-auth/index.js:105-113,146-158`: both the email-verify and OAuth-callback flows 302 to **any attacker-supplied `redirect_to`** with `#access_token=…&refresh_token=…` in the fragment. Send a victim a link to the *legitimate* project gateway with `redirect_to=https://evil.example` → victim completes a real Google login → attacker receives the tokens. Supabase enforces a per-project allow-list for exactly this. Fix: exact-origin allow-list, default `siteUrl` only.

### 9. Secrets hygiene: live production credentials on disk; rotate before launch
`apps/rachbase-backend/.env` holds **live** secrets: `rzp_live_…` Razorpay key+secret (forge any payment signature), JWT access secret (mint admin tokens), the deploy SSH private key (root on every tenant VM), GitHub App private key, `RACHBASE_SERVICE_TOKEN` (guards `/internal/run-command` → command exec on tenant VMs), plus Anthropic/Brevo/GoDaddy/Grafana keys and `DB_PASSWORD=King@2`. The top-level `secrets/` dir holds the OAuth signing key and mTLS CA key.
**Good news (I verified this myself):** neither `.env` nor `secrets/` is tracked in git — `git ls-files` is clean and there's no history for them. So this is disk/copy exposure (backups, laptop, zips — including any snapshot of this folder), not public-history exposure. Still: `secrets/` is **not in .gitignore** (one `git add -A` away from being committed), and `docker-compose.yml` boots from `.env.example` whose duplicate-line quirk leaves `RACHBASE_SERVICE_TOKEN=chan` (4 chars) while `validateEnv`'s placeholder blacklist misses `change_me*`. **Do rotate** the Razorpay secret, JWT secrets, SSH deploy key, and GitHub App key before launch (cheap insurance, and JWT rotation logs everyone out — better now than after), add `secrets/` to .gitignore/.dockerignore, and fix the compose/example landmines. One file that IS tracked in git and must go: `apps/rachbase-backend/scripts/invoice-input.json` — **real customer PII** (name, order, ₹9,400/mo).

### 10. The SLA machinery can't see outages, and you publish two different SLAs
The status prober runs **inside the rachbase-backend process and writes to the same Postgres it probes** (`server.js:29`; `statusProber.js:52-57`). When the backend or DB is down, no failing probe can be recorded; `uptimePct` counts only recorded probes and probe-less gaps render as `none`, not `down` — so a 6-hour outage shows as 100% uptime, on a status page that is itself down during the outage. Meanwhile `/sla` says **99.95%** and `/legal/sla` says **99.9%** with a different credit table; the footer links to one, the sitemap to the other. Also `GET /api/status` loads ~500k probe rows per uncached hit (`statusService.js:89-95`), unauthenticated — the status page can help kill the DB during the incident it's reporting.
**Fix for launch:** external synthetic monitor (UptimeRobot/Better Stack) as the source of truth; treat probe-gaps as unknown/down; pre-aggregate daily buckets in SQL + 30s server cache; **keep one SLA page at 99.9% (or 99.5% with credits)**.

## P1 — Fix in the 10 days if possible; week 1 otherwise

**Money & correctness.** Starter→Pro upgrade silently no-ops while the UI shows "Subscription Active!" (`proSubscription.js:171`; `checkout/page.tsx:648`) — lost upsell + lying success screen. Allowance identity is status-based and is lost across a base halt/recovery, overcharging ₹500/mo (`proSubscription.js:235`). Currency isn't locked per tenant (mixed ₹ base + $ containers; self-declared India address gets RoW customers ~48% off — `containerBilling.js:23-33`). Allowance race: two concurrent first checkouts both come online free (`beginOnline` counts outside any lock). Webhook events are de-duplicated **before** processing — a crash mid-handler loses the event forever (`paymentController.js:115-118`). Retired `svc` SKU still `orderable: true` in catalog.json.

**Security.** `trust proxy` is never set → behind Railway/nginx all IP rate-limit buckets collapse to one (global 5/h signup = platform-wide signup DoS; login limiter degenerates to per-email = anyone can lock any user out); `lib/geo.js:12` trusts spoofable XFF, which feeds **invoice tax country** (`invoiceController.js:122`). Endpoint monitoring is a tenant-driven SSRF with PUT/DELETE against internal networks incl. the metadata endpoint and the unauthenticated filer (`endpointProber.js:38-57`) — restrict to GET/HEAD + block private ranges. baas-storage/auth authorize on the spoofable `x-baas-role` header instead of verifying the gateway's internal JWT (`baas-storage/index.js:34`, `baas-auth/index.js:165`) — defense-in-depth around your main tenant boundary (verify k8s NetworkPolicies actually block cross-namespace traffic). CORS: `CORS_ORIGINS=*` reflects origin **with credentials** (`app.js:45-58`) — one config value from cross-site account access. `/api/agent/sessions*` routes reference handlers that don't exist → guaranteed 500s (`routes/agent.js:30-35`).

**Reliability.** All five baas-* services crash on an idle DB pool error (no `pool.on('error')` — the control plane has it, copy it) and none handles SIGTERM: with replicas:1 and **no liveness/readiness probes rendered** (`manifests.js`), every rollout is a per-project outage. Storage upload limit is configured, exported… and never read — `PUT /v1/object` streams unbounded bodies into the shared filer (`baas-storage/index.js:64-67`). No operator alerting at all (all email goes to customers): wire dead-letter counts + prober state transitions to Slack/PagerDuty. `unhandledRejection` tears down the process and exits 0 (`server.js:66,77`). RUNBOOK-ingress says "restart applies migrations" but nothing runs migrations on boot — and the migration runner takes no advisory lock and the tree has duplicate sequence numbers (022×2, 056×2). Control-plane pool: max 10, no `statement_timeout`; gateway/storage proxies have no upstream timeout. Data-plane hard-depends on control-plane introspection with a 30s cache — add stale-on-error so a control-plane blip doesn't take down every customer API.

**Frontend money paths (your target customer sees these in week 1).** The service page quotes **USD to India customers**: hardcoded "$10/mo per additional container", "+$10/+$20" compute strings (`services/[sid]/page.tsx:189,196,338-352`) vs the actual ₹500/₹400/₹800 they'll be charged. Checkout Payment Summary hardcodes `currency="USD"` as fallback — an INR cart renders **"$500.00"** whenever the tax quote is loading or fails (`checkout/page.tsx:1153`). The billing page's copy of OrderDetailModal still defaults to ₹/en-IN — the exact bug the "fix currency symbol" commit fixed in the *other* copy (`billing/page.tsx:144-150`; there are 5 money formatters — consolidate). Credit purchase: after Razorpay collects money, verify errors are swallowed (`catch { /* ignore */ }`, `billing/page.tsx:566-576`) — paid, no credits, no error; and the script loader has no `onerror`, so adblock = button spins forever. Service page has no catch on load — an API 500 tells the customer "Service not found" about their paid container.

**Broken assets.** Every page renders a broken logo: `BrandLogo.tsx` points at `/brand/rachbase-logo.png` which doesn't exist (only rach-dev SVGs are in public/). `public/illustrations/pages/` is empty but 7 marketing pages reference PNGs in it; `/arka-microstacks.png` referenced on homepage + billing is missing.
